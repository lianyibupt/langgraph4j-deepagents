## 用户目标

用熟悉的 Java 从零理解、实现并调试 Agent。最终覆盖两个任务：

- A：读取指定源码仓库，检索代码，解释架构，生成包含文件位置的研究报告。
- B：读取指定 Markdown 文档目录，检索知识，整理有来源的笔记。

开发方式是逐阶段交付，每阶段具备运行入口、验证用例、调试路径和认知说明。每次只推进一个清晰的学习阶段，用户运行并讨论后再扩展下一阶段。

## 路线选择

采用自写小型 Java 内核、按需引入模型适配库的路线。LangGraph4j 和 Python Deep Agents 用来对照理解其设计；第一阶段不依赖现有 Java 示例的图运行时。

备选方案是直接扩展现有 Java 示例，起步快，但不利于逐步观察内核；或系统性移植 Python 框架，范围较大。当前以学习与个人使用为验收目标，暂不建设通用框架。

新增实现放在当前仓库下的 `personal-agent/`，便于在同一工作区与参考源码对照。它拥有独立的运行入口，不修改原项目的 `pom.xml`、Java 源码或现有 Wiki。未来可独立迁出为仓库。

## 分阶段路线

| 阶段 | 可运行成果 | 要理解的机制 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 纯 JDK、离线可复现的 Agent 循环实验 | 模型提出工具调用，程序执行并回填结果，再由模型结束 | 工具调用关联正确、状态可观察、循环有上限 |
| 2 | 接入真实模型的终端 Agent | 消息协议、工具 Schema、供应商适配、真实模型的不确定性 | 同一个运行时支持模型替身和真实模型；错误能定位 |

| 4 | Markdown 知识 Agent（B） | 文档检索、来源归属、笔记生成和产物保存 | 原始文档只读；新笔记进入专门输出目录 |

| 6 | 子 Agent 与恢复 | 独立上下文、结构化委派结果、检查点和恢复语义 | 委派边界清楚；恢复不盲目重放带副作用的工具 |

阶段不是承诺一次性全部实现。阶段 2 的模型供应商与依赖选型，在接入前依据用户可用模型和当前官方接口确定。

## 第一阶段的明确范围

目标：运行一个完整且可断点调试的“模型—工具—模型”循环。使用脚本模型替身，响应顺序固定，不调用真实模型、不使用 API Key。替身仅用于验证运行机制，不具有推理能力，运行输出必须标明 `scripted`。

示例问题：读取自带 Markdown 资料中关于 Agent Loop 的解释并回答。模型替身第一轮请求 `read_text`；运行时读取样例文件，把工具结果追加到消息历史；替身第二轮核对工具结果并返回结束消息。

第一阶段只处理文本消息，以及模型一次响应中的一个或多个工具调用。工具串行执行。模型接口一次返回“最终文本”或“工具调用列表”，不同时表达两者。暂不加入流式响应、并行执行、网络搜索、向量数据库、子 Agent、跨会话记忆或真实文件写入工具。

### 数据流

1. CLI 构造用户消息和读取工具，创建运行时。
2. 运行时把当前消息历史的只读快照传给 `ModelClient`。
3. 收到最终响应时，追加助手消息并结束。
4. 收到工具调用时，先记录包含调用 ID 的助手消息。
5. 逐个执行工具，把对应调用 ID 的结果追加到历史。
6. 再调用模型，使其能看见完整的调用和结果。
7. 达到模型轮次上限时返回明确的停止状态，不伪装为完成。

### 状态与错误

- 第一阶段状态包含消息历史和最终停止原因；不使用跨进程检查点。
- 工具不存在、参数不合法、目标不存在或读取失败，以结构化工具错误回填，给模型下一轮处理的机会。
- 模型自身抛出异常或返回非法响应时，任务返回明确失败原因并保留已有历史。
- 工具调用 ID 必须非空且在单次运行内唯一；重复 ID 在执行工具前被拒绝。
- 最大模型轮次必须为正整数；限制在请求下一轮模型之前检查。
- 异常处理不捕获 JVM 致命错误，不做无限自动重试。

### 文件读取边界

- 示例资料独立存放，默认只访问自带样例目录。
- 工具只接受相对于工作目录的路径，拒绝绝对路径和越出根目录的路径。
- 以真实路径检查符号链接解析后的目标仍在工作根目录内。
- 只读取常规 UTF-8 文件，第一阶段限制单次读取字节数，超限返回明确错误。
- 该路径检查是学习版文件访问约束，不宣称提供对抗本机并发恶意文件替换的操作系统沙箱。
- 后续开放用户仓库或笔记目录时，仍默认只读输入；报告保存到单独输出位置。

### 可观察性与调试

终端顺序展示：模型轮次、响应类型、工具名与调用 ID、工具执行结果摘要、下一次模型输入的消息数量以及结束原因。示例允许查看自带资料的消息内容；不默认打印未来真实模型的凭证或完整个人文档。

README 提供两种调试方式：IDE 在 `Main` 启动后设置断点，或通过 JDK 的 JDWP 启动参数等待调试器连接。建议依次观察四个断点位置：模型调用前、收到模型响应后、执行工具时、把结果追加到消息历史后。

每阶段附带一个实验。第一阶段至少包括：改变样例文字、读取不存在文件、把最大模型轮次改为 1，并说明这些操作分别展示了什么机制。

### 第一阶段验证

采用可执行 Java 行为测试，断言失败时进程返回非零退出码，不依赖默认关闭的 Java `assert`。

必须验证：

1. 一次读取工具后能够结束，工具结果在下一次模型输入中可见，且调用 ID 匹配。
2. 模型直接给出最终答案时不执行工具。
3. 不存在工具和读取失败会形成工具错误消息。
4. 多个工具调用各自收到正确关联的结果。
5. 轮次上限能阻止继续请求模型，停止原因准确。
6. 重复调用 ID 被拒绝，不重复执行工具。
7. 模型异常返回失败状态，历史保留。
8. 路径穿越、绝对路径和指向根目录外的符号链接被拒绝；正常 UTF-8 样例可读；超限读取失败。

先观察测试因缺失行为失败，再实现最小代码并验证通过。最后执行 CLI 演示，核对终端事件顺序与说明一致。真实模型能力必须在阶段 2 单独验证，第一阶段通过不代表真实模型任务通过。

## A 与 B 的共同内核和差异

共同复用运行时、消息协议、模型适配、工具执行、上下文选择及报告产物接口。

A 的扩展围绕源码文件发现、文本检索、按行读取、源码引用；B 的扩展围绕 Markdown 发现、标题和正文检索、笔记引用及新笔记写入。最初均采用可解释的文件和文本检索，是否需要语义检索由实际问题决定。

报告中区分 `confirmed`、`uncertain` 和建议。源码存在不自动等于行为已在运行中验证；引用必须来自实际读取过的文件。个人知识整理不得把推断当成原文观点。
